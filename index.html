Server Stack: operator guide

Runs several Laravel Shopper shops, one Bagisto store and one Odoo ERP on a single Ubuntu 24.04 server, behind nginx with PHP-FPM, PostgreSQL, MySQL and Redis. You write your settings once in .env, and the scripts generate every config file from it.

1. What this is

A folder (/srv/stack on the server) with three kinds of content:

PartWhat it isYou…
.envYour real values: domains, email, mail password, which sites to run. Git-ignored.edit this
sites/<name>/Plain PHP/HTML websites kept in the repo (e.g. the shop1 page)edit your pages here
bin/*.shScripts that install, configure, deploy and remove thingsrun them
stack.env, instances/*.envCommitted defaults (placeholders). Real values go in .envrarely touch
templates/, nginx/, php/, postgres/…Config blueprints the scripts fill inonly for tuning
secrets/Passwords generated on the server (DB, Redis, Odoo). Git-ignored.back up, never edit

How a request travels:

browser ─► nginx :443 ─┬─► shop1.yourdomain  ─► PHP-FPM pool "shopper1" (PHP 8.3) ─► PostgreSQL + Redis
                       ├─► shop2.yourdomain  ─► PHP-FPM pool "shopper2"            ─► PostgreSQL + Redis
                       ├─► store.yourdomain  ─► PHP-FPM pool "bagisto"             ─► MySQL + Redis
                       └─► erp.yourdomain    ─► Odoo :8069 / websocket :8072       ─► PostgreSQL

Each site (an instance) has its own Linux user, its own PHP pool, its own database and its own folder /srv/apps/<name>. One broken or hacked site can't touch another.

2. Before you start

  • A server with Ubuntu 24.04 LTS, at least 4 GB RAM (8–16 GB for all apps), and root SSH access.
  • A DNS A record for each domain pointing to the server IP (section 8). SSL certificates only work once DNS resolves.
  • This repo on GitHub (private). The server clones it.
  • For Laravel apps deployed from git: a repo per app, plus a deploy key (recipe).
Running as rootCommands are written with sudo. If you're logged in as root they work the same; sudo is simply ignored.

3. First install

  1. On your PC, create your settings file from the template and fill it in (at minimum INSTANCES, LETSENCRYPT_EMAIL and each instance's __SERVER_NAME): 
    cp .env.example .env
  2. Log in to the server: 
    ssh root@SERVER_IP
  3. Give the server read access to this repo. The repo is private, and GitHub doesn't accept account passwords for git clone. Create a deploy key on the server: 
    ssh-keygen -t ed25519 -C "server-stack@$(hostname)" -f ~/.ssh/server_stack -N ""
cat ~/.ssh/server_stack.pub
    Add the printed line on GitHub (repo → Settings → Deploy keys → Add deploy key) and leave write access unticked. Then tell SSH to use it and test: 
    printf 'Host github.com\n  HostName github.com\n  User git\n  IdentityFile ~/.ssh/server_stack\n  IdentitiesOnly yes\n' >> ~/.ssh/config && chmod 600 ~/.ssh/config
ssh -T git@github.com
    It should greet you with "Hi Khanaliasad/server-stack! You've successfully authenticated". Answer yes the first time.
  4. Get the stack onto the server, over SSH (git@github.com:…, not https://): 
    apt update && apt install -y git
git clone git@github.com:Khanaliasad/server-stack.git /srv/stack
    Already cloned over https earlier? Switch it: cd /srv/stack && git remote set-url origin git@github.com:Khanaliasad/server-stack.git && git pull
  5. Copy your .env to the server. It's git-ignored, so it's not in the clone. Run this from your PC, in a second terminal: 
    scp .env root@SERVER_IP:/srv/stack/.env
  6. Check the settings (on the server). Fix any ERROR lines in /srv/stack/.env: 
    cd /srv/stack && sudo bin/show-config.sh
  7. Build everything. It installs packages, configures services, creates each site, publishes pages and gets certificates. It takes about 10–15 minutes and is safe to re-run. 
    sudo bin/setup.sh
    If it stops with an error: fix the cause (or git pull a fix), then continue without repeating the slow package step. Everything already done is kept: 
    cd /srv/stack && git pull && sudo bin/setup.sh --skip-install
  8. Open the site: https://shop1.yourdomain. A new Laravel instance shows a stack check page (PHP version, extensions, database, Redis). A sites/<name>/ folder, like shop1's phpinfo page, replaces it.
If a certificate failsDNS isn't pointing at the server yet. Fix the A record, wait a few minutes, then run sudo bin/issue-cert.sh shopper1.

4. The .env file

/srv/stack/.env is the one file you edit. It's git-ignored, so it never reaches GitHub. Keep a copy somewhere safe, such as a password manager. The template with every option is .env.example.

Four kinds of keys

FormApplies toExample
KEY=valuewhole server (overrides stack.env)LETSENCRYPT_EMAIL=asad@hsaverse.shop
NAME__KEY=valueone instance (overrides instances/name.env)SHOPPER1__SERVER_NAME="shop1.hsaverse.shop"
APPENV_KEY=valuewritten into every Laravel app's shared/.env as KEY=valueAPPENV_MAIL_HOST=smtp-relay.brevo.com
NAME__APPENV_KEY=valuewritten into one app's shared/.envSHOPPER1__APPENV_MAIL_FROM_NAME="Shop One"

NAME is the instance name in capitals, with - turned into _: shopper1 → SHOPPER1__, my-shop → MY_SHOP__. There are two underscores.

Syntax rules

  • No spaces around =. Wrong: KEY = value. Right: KEY=value.
  • Put values containing spaces in quotes: SHOPPER1__SERVER_NAME="shop1.x.com www.shop1.x.com".
  • Use single quotes for values containing $, which is common in passwords: APPENV_MAIL_PASSWORD='ab$cd'.
  • An empty APPENV_ value is skipped, so the app keeps its current value.
  • Lines starting with # are comments.
  • Editing on Windows (Notepad, VS Code) is fine: the scripts strip Windows line endings when they read env files.

Load order (later wins)

stack.env→.env global keys→secrets/stack.env→instances/<name>.env→secrets/<name>.env→.env NAME__ keys

So SHOPPER1__PHP_VERSION=8.4 in .env beats PHP_VERSION=8.3 in instances/shopper1.env. Run sudo bin/show-config.sh any time to see the final values.

6. Command reference

Run everything from /srv/stack on the server. Scripts marked safe to re-run never overwrite your data or passwords.

bin/setup.sh safe to re-run

Does everything in order: checks config → installs packages → configures services → creates each site in INSTANCES → publishes sites/ pages → gets certificates.

When
First install; after adding a site to INSTANCES; after git pull of the stack
Usage
sudo bin/setup.sh
Options
--skip-install skip the (slow) package step · --no-certs skip SSL

bin/show-config.sh read-only

Prints the final settings of each site after all overrides. Flags placeholders, duplicate domains, duplicate Redis DBs and duplicate ports. Masks passwords.

When
After every .env edit, before running anything else
Usage
sudo bin/show-config.sh · sudo bin/show-config.sh shopper1 bagisto

bin/00-install-base.sh safe to re-run

Installs system packages: nginx (nginx.org), PHP versions + extensions, PostgreSQL, MySQL, Redis, Node.js, supervisor, certbot, composer.

When
First install (via setup.sh); after changing PHP_VERSIONS / PG_VERSION / NODE_MAJOR
Usage
sudo bin/00-install-base.sh

bin/10-configure-services.sh safe to re-run

Links the stack's configs into nginx, PHP, PostgreSQL, MySQL and Redis. Generates the Redis password, tunes the kernel, and enables the firewall (80, 443 and the port sshd actually listens on, even a custom one). Backs up the original configs first.

When
First install; after changing files in nginx/, php/, postgres/, mysql/, system/
Usage
sudo bin/10-configure-services.sh

bin/create-instance.sh <name> safe to re-run

One-time setup of a site: Linux user, /srv/apps/<name> folders, database + user with a random password, the Laravel shared/.env (with APPENV_ values), and the stack check page. It also repairs a user left over from an earlier failed attempt (missing home folder).

When
Once per new site (setup.sh does it)
Usage
sudo bin/create-instance.sh shopper2
Note
An existing shared/.env or secrets file is never overwritten

bin/render.sh <name> safe to re-run

Regenerates the site's nginx config, PHP-FPM pool, queue workers (and for Odoo its config + service) from the templates and your settings. Tests them, then reloads the services.

When
After changing any NAME__ setting
Usage
sudo bin/render.sh shopper1
Note
Stops with an error if a required setting is missing, so nothing half-configured goes live

bin/publish-site.sh <name>

Makes sites/<name>/ from this repo the live web root (a new release, switched instantly). For plain PHP/HTML sites like the shop1 page.

When
After editing and pulling a page in sites/
Usage
sudo bin/publish-site.sh shopper1

bin/issue-cert.sh <name> safe to re-run

Gets a free Let's Encrypt SSL certificate for every domain in SERVER_NAME, then re-renders. Renewal is automatic.

When
After DNS points at the server; after adding or changing a domain
Usage
sudo bin/issue-cert.sh shopper1

bin/deploy-laravel.sh <name> [branch|tag] [options]

Zero-downtime deploy of a Laravel app from its git repo: clone → composer → npm build → storage:link + shopper:link (recreates the admin's public/cpanel link for each release) → database backup (only if migrations are pending) → migrate → optional seeders → cache → write a release record → switch current → reload PHP → restart workers. Keeps the last 5 releases and the last 5 backups.

When
Every time you release app code
Usage
sudo bin/deploy-laravel.sh shopper1 · sudo bin/deploy-laravel.sh shopper1 v1.2.0 · sudo bin/deploy-laravel.sh shopper1 v1.2.0 --seed=CategorySeeder
Options
--seed runs DatabaseSeeder · --seed=Class runs one seeder (repeat for more) · --backup always back up first · --no-backup never back up · --artisan="cmd" one extra artisan command, this deploy only
App commands
From settings: RUN_SHOPPER_SETUP (shopper:setup with the SETUP_* values), FIRST_DEPLOY_ARTISAN, DEPLOY_ARTISAN. Order: migrate → seeders → app commands → cache → switch. If one fails, the new version doesn't go live
If it fails
The live site keeps its old code. If it failed after migrations ran, it prints the exact command to undo them (details)
Needs
NAME__REPO_URL + a deploy key (recipe)

bin/rollback.sh <name> [release] [mode] changes the live site

Switches a Laravel site back to an earlier release. If the database changed since then, it shows exactly which migrations would be undone, previews the SQL, and makes you type the count before doing anything. Nothing older than the target release is ever touched.

When
A deploy broke something and you want the previous version back
Usage
sudo bin/rollback.sh shopper1 --list (only shows, changes nothing) · sudo bin/rollback.sh shopper1 (one release back, asks what to do) · sudo bin/rollback.sh shopper1 20261001120000 (a specific release)
Modes
--with-migrations undo the newer migrations, then switch · --code-only switch the code only · --restore-backup restore the pre-deploy backup (loses all data since; asks you to type RESTORE) · --yes no questions (needs a mode)
More
How the rollback decides and counts

bin/shopper-setup.sh <shop> [--dry-run]

Runs your app's php artisan shopper:setup on the live release, building the options from the shop's SETUP_* settings in .env: admin email and password, store name and email, country, currencies, street, postal code, city.

When
Setting up a shop that's already deployed (so its first deploy is past), or re-running the setup after changing the values
Usage
sudo bin/shopper-setup.sh shopper1 --dry-run (shows the command, password hidden, runs nothing) · sudo bin/shopper-setup.sh shopper1
Needs
At least NAME__SETUP_ADMIN_EMAIL and NAME__SETUP_ADMIN_PASSWORD. It stops with a clear message if they're empty

bin/sync-env.sh <name> safe to re-run

Writes the APPENV_ values from .env into the app's shared/.env, then refreshes Laravel's config cache, PHP and the workers.

When
After changing mail or any other APPENV_ key
Usage
sudo bin/sync-env.sh shopper1

bin/install-odoo.sh <name> safe to re-run

Installs Odoo's build libraries, wkhtmltopdf (PDF reports) and rtlcss. Clones/updates the Odoo source, builds the Python venv, initialises the database, and starts the service.

When
First Odoo install (setup.sh does it); to pull Odoo updates
Usage
sudo bin/install-odoo.sh odoo

bin/check-php-ext.sh [version] read-only

Checks that every PHP extension Laravel, Shopper and Bagisto need is present, for both CLI and FPM, and prints the apt install fix for anything missing.

Usage
bin/check-php-ext.sh 8.3 · bin/check-php-ext.sh 8.4 laravel shopper

bin/uninstall.sh [names] [options] removes things

Undoes the setup. By default it removes only generated settings. Packages, .env files, passwords, app files, databases and certificates are kept, and setup.sh brings everything back.

Usage
sudo bin/uninstall.sh --dry-run (preview) · sudo bin/uninstall.sh (all settings) · sudo bin/uninstall.sh shopper2 (one site)
Delete more
--apps files + user · --databases · --certs · --secrets · --packages (also wipes DB data) · --everything. Any of these needs you to type DELETE
Kept always
The firewall stays on; /srv/stack and your .env stay

7. How to…

Update the main website (hsaverse.shop)

The main domain is the website instance: type site, a plain PHP/HTML site with no database, no Laravel and no workers. Its files live in this repo at sites/website/.

  1. On your PC, edit sites/website/index.php. It's a single self-contained intro page: hero, stores, "why us", how it works, contact. The texts, store names and links are plain HTML, so search for the words you want to change. Colours are CSS variables at the top of <style> (--violet, --cyan, --pink). Put images in the same folder, then commit and push.
  2. On the server: 
    cd /srv/stack && git pull && sudo bin/publish-site.sh website

Any site type can be published from sites/<name>/ the same way. shopper1 used sites/shopper1/ (the phpinfo page) until its first Laravel deploy.

A second plain site: copy instances/website.env to instances/<name>.env, set APP_NAME=<name>, create sites/<name>/index.php, add <NAME>__SERVER_NAME + the name to INSTANCES in .env, then run sudo bin/setup.sh --skip-install.

Only index.php runs as PHPBy design, other .php files return 404. Route extra pages through index.php (e.g. index.php?page=about) or use .html files. Remove phpinfo() before going public.

Add another website (e.g. shopper2)

  1. Add a DNS A record, e.g. shop2 → server IP.
  2. In /srv/stack/.env: 
    INSTANCES="shopper1 shopper2"
SHOPPER2__SERVER_NAME="shop2.hsaverse.shop"
  3. Check and apply: 
    sudo bin/show-config.sh
sudo bin/setup.sh --skip-install

For a brand-new name (e.g. shopper3), first copy the instance file, then edit its <-- UNIQUE lines (APP_NAME, DB_NAME, DB_USER, REDIS_DB, REDIS_CACHE_DB):

cp instances/shopper2.env instances/shopper3.env

Deploy a Laravel app from GitHub

Each site runs as its own Linux user, so each site needs its own deploy key, even when two sites deploy the same repo (shopper1 and shopper2 both use Khanaliasad/shopper). GitHub allows several deploy keys on one repo. Don't reuse the server-stack key: GitHub allows a key on one repo only.

  1. Create a key for each site's user and print it (run after setup.sh has created the users): 
    for u in shopper1 shopper2; do
  sudo -u $u -H ssh-keygen -t ed25519 -N "" -f /srv/apps/$u/.ssh/id_ed25519 -C "$u@server"
  sudo cat /srv/apps/$u/.ssh/id_ed25519.pub
done
  2. On GitHub, go to the app repo → Settings → Deploy keys → Add. Add each printed line as its own key, read-only.
  3. Trust GitHub once per user: 
    for u in shopper1 shopper2; do sudo -u $u -H ssh -o StrictHostKeyChecking=accept-new -T git@github.com; done
  4. Set SHOPPER1__REPO_URL=git@github.com:Khanaliasad/shopper.git (same for SHOPPER2__) in .env, then deploy: 
    sudo bin/deploy-laravel.sh shopper1
sudo bin/deploy-laravel.sh shopper2
    The first deploy replaces the check page / sites/ page and starts the queue workers. Apps without a package-lock.json are built with npm install instead of npm ci.
  5. First time only, set up the shop (admin user + store details). Fill in the SHOPPER1__SETUP_… values in /srv/stack/.env (keys). With SHOPPER1__RUN_SHOPPER_SETUP=first, the first deploy runs shopper:setup by itself. For a shop that's already deployed, run it directly: 
    sudo bin/shopper-setup.sh shopper1 --dry-run    # check the command first
sudo bin/shopper-setup.sh shopper1
    Bagisto: run artisan bagisto:install as the site user.

Set up email for the Laravel apps

  1. Create a free Brevo account and verify your domain (DNS records in section 8).
  2. Copy the SMTP login and key from Brevo → SMTP & API into .env: 
    APPENV_MAIL_USERNAME=your-login@smtp-brevo.com
APPENV_MAIL_PASSWORD='your-smtp-key'
APPENV_MAIL_FROM_ADDRESS=noreply@hsaverse.shop
  3. Push to each app: 
    sudo bin/sync-env.sh shopper1

Change a site's PHP version

# the version must be in PHP_VERSIONS (installed); check its extensions first
bin/check-php-ext.sh 8.4
# .env:  SHOPPER1__PHP_VERSION=8.4
sudo bin/render.sh shopper1

The site moves to the new PHP immediately. The nginx config doesn't change. The workers, composer and artisan follow on the next deploy (or run sudo bin/deploy-laravel.sh shopper1).

Change or add a domain

# .env:  SHOPPER1__SERVER_NAME="shop1.hsaverse.shop www.shop1.hsaverse.shop"
#        SHOPPER1__APPENV_APP_URL=https://shop1.hsaverse.shop
sudo bin/render.sh shopper1
sudo bin/issue-cert.sh shopper1
sudo bin/sync-env.sh shopper1

Give a busy site more capacity

# .env:  SHOPPER1__FPM_MAX_CHILDREN=40   SHOPPER1__QUEUE_WORKERS=4
sudo bin/render.sh shopper1

Rule of thumb: total FPM_MAX_CHILDREN across all sites × ~100 MB must fit in the RAM you can spare for PHP.

Install Odoo

# DNS: erp → server IP.   .env:  INSTANCES="shopper1 odoo"   ODOO__SERVER_NAME="erp.hsaverse.shop"
sudo bin/setup.sh --skip-install

Log in at https://erp.hsaverse.shop as admin / admin and change the password immediately.

Roll back a bad deploy

# 1. look first: this changes nothing
sudo bin/rollback.sh shopper1 --list
# 2. go one release back; the script explains what it will do and asks before each change
sudo bin/rollback.sh shopper1

12. Security checklist

  • Keep the GitHub repo private. Never commit .env or secrets/ (already git-ignored).
  • .env is mode 600 (setup.sh enforces it). Keep a copy in a password manager.
  • Remove phpinfo() from public pages once testing is done.
  • Use SSH keys and disable password login (PasswordAuthentication no in /etc/ssh/sshd_config) once your key works.
  • APP_DEBUG=false in every production app.
  • Change Odoo's admin password on the first login.
  • Databases and Redis only listen on localhost. The firewall allows only SSH, 80 and 443.
  • Run sudo apt update && sudo apt upgrade monthly (security updates for PHP, nginx and the rest).

Every deploy builds a complete fresh copy next to the live one, then switches over in a single instant:

/srv/apps/shopper1/
├── current  →  releases/20261002143000     ← live site (just a pointer)
├── releases/
│   ├── 20261001120000                       ← previous release, kept for rollback
│   └── 20261002143000                       ← newest
└── shared/                                  ← survives every release
    ├── .env                                 config + passwords
    └── storage/                             uploads, logs, cache
  1. Clone your repo into a new releases/<date-time>. The live site keeps running meanwhile.
  2. Link shared/.env and shared/storage, so settings and uploads carry over.
  3. Build: composer install, npm run build, migrations, Laravel caches.
  4. Switch: current moves to the new folder in one step, only if everything above succeeded. A failed deploy leaves the live site untouched.
  5. Refresh: PHP reloads, queue workers restart, and only the last 5 releases are kept.
Why not git pull in the live folder?Visitors would see half-updated files. It would skip composer, the build, migrations and the caches, leave the code stale in OPcache, and leave no clean way back.

15. Migrations, seeders & rollback

What a deploy does with the database

ItemBehaviour
Migrationsartisan migrate --force runs on every deploy, in the new release, before current switches. If a migration fails, the deploy stops and the live site keeps its old code
SeedersOnly when you ask: --seed=Class on the deploy command runs them after migrations, before the switch (below)
DatabaseOne per site (shopper1, shopper2), shared by every kept release
Backup before deployAutomatic when migrations are pending: a full copy goes to /srv/apps/<site>/shared/backups/ (the last 5 are kept, root-only). --backup forces one; --no-backup skips it
Release recordEach release folder gets a .release file with its git tag/branch, commit, deploy time, database batch before/after, backup file and seeders. rollback.sh reads it. It sits outside public/, so it's never served

What the deploy prints about the database

==> Database: batch 6, 1 pending migration(s)
==> Backing up shopper1 -> /srv/apps/shopper1/shared/backups/20261002143000-before-a1b2c3d.dump
==> Migrating
==> Deployed shopper1 @ v1.3.0 (a1b2c3d)  migrations: batch 6 -> 7  backup: …

Batch is Laravel's counter of migrate runs. batch 6 -> 7 means this deploy changed the database once. batch 6 -> 6 means it didn't change it at all.

If a deploy fails halfway

  • Failed before migrations (composer, npm build): nothing changed. The live site and database are exactly as before.
  • Failed after migrations (a seeder or the cache step): the live site still runs the old code, but the database already has the new schema. The deploy prints a warning with the exact command to undo it, run from the failed release, which has the migration files:
!! Deploy failed AFTER migrations ran. The live site still runs the old code,
!! but the database already has the new schema (batch > 6).
!! Undo the migrations from the failed release (it has the migration files):
     sudo -u shopper1 -H /usr/bin/php8.3 /srv/apps/shopper1/releases/20261002143000/artisan migrate:rollback --force
!! Pre-deploy backup: /srv/apps/shopper1/shared/backups/20261002143000-before-a1b2c3d.dump

This undoes only the batch that failed deploy created. Or fix the problem and deploy again: the new deploy sees the migrations as already done.

releases/20261001  (old code) ─┐
releases/20261002  (new code) ─┼──►  ONE database: shopper1
current → 20261002             ─┘    (already has the new schema)
Rolling back code does not roll back the databaseAfter switching current back, your old code runs against the new schema. Whether that works depends on what the migration did.

Will the old code survive the new schema?

The new release's migration…Old code after rollback
Added a table✅ fine: old code ignores it
Added a nullable column, or one with a default✅ fine
Added a NOT NULL column without a default❌ old code's inserts fail
Renamed a column / table❌ old code queries the old name and crashes
Dropped a column / table❌ crashes, and the data is gone
Changed a column type⚠️ depends on the change

The rollback script: how it decides and counts

sudo bin/rollback.sh shopper1 does this, in order, and changes nothing until you confirm:

  1. Lists the releases, with their tag, commit, deploy time and database batch. The live one is marked *. 
    Releases of shopper1 (database is at migration batch 7):
    RELEASE            REF          COMMIT    DEPLOYED          MIGRATIONS / BACKUP
    20261001120000     v1.2.0       9f8e7d6   2026-10-01 12:00  batch 5 -> 6
  * 20261002143000     v1.3.0       a1b2c3d   2026-10-02 14:30  batch 6 -> 7, backup
  2. Picks the target: the release just before the live one, or the one you name.
  3. Compares batches. The target's record says the database was at batch 6 while it was live, and the database is now at batch 7.
  4. Lists only the migrations in batches above the target's, by name, straight from the database. Their count is the exact number of steps: 
    The database is at batch 7; 20261001120000 expects batch 6.
Only these 1 migration(s), from the 1 newer batch(es), would be undone
(batch  migration). Everything at batch 6 and older stays as it is:
  7  2026_10_02_000000_drop_old_price_column
  5. Asks what you want: 1) undo those migrations, then switch · 2) code only · 3) restore the backup · q) cancel.
  6. Dry run. For option 1, it prints the SQL the undo would run (migrate:rollback --pretend). Nothing has changed yet.
  7. You type the number (1 here) to confirm. Any other answer aborts with nothing changed.
  8. Undoes exactly that many steps (migrate:rollback --step=1), from the live release, which has the migration files. It then checks the database is back at the target's batch. If not, it stops without switching the code.
  9. Switches current to the target, reloads PHP and restarts the queue workers.
SituationWhat the script does
No migrations newer than the targetSays a code-only rollback is safe, and only switches the code
Going back several releasesCounts every migration in all batches above the target (e.g. batches 6 and 7 = 3 migrations) and undoes exactly those
The target is at batch 0Refuses: that would undo every migration and empty the database
The target has no release record (deployed before this feature, or a bootstrap/site page)Refuses --with-migrations (it can't know what to undo). Code-only or restore-backup are still possible
Restore-backup chosenUses the backup the next deploy took (the database as it was while the target was live). Maintenance mode on, workers stopped, restore, switch, back online. You must type RESTORE
Releases deployed before this update have no recordOnly deploys made with the new script can be rolled back with migrations. Deploy once after pulling this update, so the next rollback has records to work with.

Rolling back safely: three options, best first

1. Write migrations old code survives ("expand, then contract"). This is standard practice, and it makes 99% of rollbacks code-only. Never rename or drop in the same release that stops using something:

  1. Release A: add the new column (nullable). The code writes to both the old and new column.
  2. Release B: the code reads the new column. A migration copies old data across.
  3. Release C, once B is proven stable: drop the old column.

2. Undo the migration with migrate:rollback. bin/rollback.sh does this for you, with the count and checks above. The manual steps below are what it does under the hood, in case you ever need them. Laravel records each migrate run as a numbered batch in the migrations table, and migrate:rollback runs the down() methods of the last batch. Order matters: run it from the new release, which contains the new migration files, before switching back. The old release doesn't know those migrations exist, so the rollback fails from there.

# 1. see which batch the last deploy created
sudo -u shopper1 -H php8.3 /srv/apps/shopper1/current/artisan migrate:status
# 2. undo it — still from the NEW release (current)
sudo -u shopper1 -H php8.3 /srv/apps/shopper1/current/artisan migrate:rollback --step=1 --force
# 3. only now switch the code back
ls /srv/apps/shopper1/releases/
sudo -u shopper1 ln -sfn /srv/apps/shopper1/releases/<older-folder> /srv/apps/shopper1/current
sudo systemctl reload php8.3-fpm
sudo -u shopper1 -H php8.3 /srv/apps/shopper1/current/artisan queue:restart

--step=1 undoes one migration file. Use migrate:rollback --force without --step to undo the whole last batch (everything one deploy ran). A deploy with no new migrations creates no batch, so check migrate:status first. Preview what a migration will do before deploying: artisan migrate --pretend.

down() can destroy dataA down() that drops a column also deletes everything written into it since the deploy, including orders and customer data. Read the migration's down() before running it.

3. Restore a database backup. This is the safest option for a disaster, but you lose every order and signup made since the backup. On a live shop, use it only if option 2 is impossible. The easy way is sudo bin/rollback.sh shopper1 --restore-backup, which uses the backup the deploy took automatically. By hand:

# backups taken by deploys
sudo ls -lh /srv/apps/shopper1/shared/backups/
# take one yourself before something risky
sudo -u postgres pg_dump -Fc shopper1 > /backup/shopper1-before-v1.3.dump
# restore (stop the site's workers first: sudo supervisorctl stop 'shopper1:*')
sudo -u postgres pg_restore --clean --if-exists -d shopper1 < /backup/shopper1-before-v1.3.dump

Custom seeders

A seeder is a class that fills the database with data you define: categories, countries, roles, default settings, demo products.

1. Create it on your PC (in the app repo, e.g. shopper):

php artisan make:seeder CategorySeeder

2. Make it safe to run more than once. On a live shop, a seeder may run twice, on both shops, or again after a fix. Use updateOrCreate / updateOrInsert / firstOrCreate, never plain create:

<?php

namespace Database\Seeders;

use Illuminate\Database\Seeder;
use Illuminate\Support\Facades\DB;

class CategorySeeder extends Seeder
{
    public function run(): void
    {
        $categories = [
            ['slug' => 'men',         'name' => 'Men'],
            ['slug' => 'women',       'name' => 'Women'],
            ['slug' => 'accessories', 'name' => 'Accessories'],
        ];

        foreach ($categories as $category) {
            // matched on slug: existing rows are updated, nothing is duplicated
            DB::table('categories')->updateOrInsert(
                ['slug' => $category['slug']],
                ['name' => $category['name'], 'updated_at' => now()],
            );
        }
    }
}

With an Eloquent model it's one line per row: Category::updateOrCreate(['slug' => 'men'], ['name' => 'Men']);. Table and model names depend on your app: Shopper has its own tables and models, so check them in your code first.

Optionally register it in database/seeders/DatabaseSeeder.php, so a plain db:seed runs it too:

public function run(): void
{
    $this->call([
        CategorySeeder::class,
    ]);
}

3. Commit and push, then 4. deploy with the seeder. This is the easy way: it runs after migrations and before the switch, so if the seeder fails, the new version never goes live:

sudo bin/deploy-laravel.sh shopper1 --seed=CategorySeeder
sudo bin/deploy-laravel.sh shopper2 --seed=CategorySeeder
# several seeders, or everything in DatabaseSeeder
sudo bin/deploy-laravel.sh shopper1 --seed=CategorySeeder --seed=BrandSeeder
sudo bin/deploy-laravel.sh shopper1 --seed
"Before the switch" is about the codeThe seeder writes into the live database, so its data is visible to the current site as soon as it runs. That's another reason to write seeders that are safe to run more than once.

Or run a seeder without deploying, on the code that's already live:

# one shop
sudo -u shopper1 -H php8.3 /srv/apps/shopper1/current/artisan db:seed --class=CategorySeeder --force
# both shops (same code, separate databases)
for s in shopper1 shopper2; do sudo -u $s -H php8.3 /srv/apps/$s/current/artisan db:seed --class=CategorySeeder --force; done
  • --class= runs only that seeder. Without it, everything in DatabaseSeeder runs.
  • --force is required in production (otherwise Laravel asks for confirmation and stops).
  • sudo -u shopper1 runs it as that site's user, so it uses that site's .env and database.

Seeder or migration?

Use a…For
SeederBase / reference data you may re-apply: categories, countries, roles, default settings, demo products on a test shop
MigrationA one-time change to live data ("mark all old products inactive", "move prices to the new column"). It runs exactly once, automatically with the deploy, in order

To have seed data arrive automatically with a deploy, exactly once, call the seeder from a migration:

public function up(): void
{
    (new \Database\Seeders\CategorySeeder)->run();
}

Git tags

The deploy script takes any branch or tag name as its second argument and deploys exactly that code. With no name, it deploys REPO_BRANCH (main). You create the tags yourself, on your PC:

# on your PC, in the app repo
git tag v1.3.0
git push origin v1.3.0
# on the server
sudo bin/deploy-laravel.sh shopper1 v1.3.0
  • A tag always means the same code, so redeploying an older tag (… shopper1 v1.2.0) is an alternative to a rollback. It builds a fresh release of that version, but still doesn't undo migrations.
  • Use semantic versions: v1.3.1 = bug fix, v1.4.0 = new features, v2.0.0 = breaking change (e.g. a migration old code can't survive).
  • List tags with git tag; see what's in one with git show v1.3.0 --stat.
  • Release folders are named by date (releases/20261002143000), but each one's .release record stores the tag and commit. See them with sudo bin/rollback.sh shopper1 --list.
